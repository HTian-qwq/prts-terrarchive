# 莱茵生命：Agent 调查线索板第一阶段调研与设计

日期：2026-09-18。状态：设计提案，未接入运行代码；尺寸、数量和时长是待验证的起点，不是已测结果。

## 1. 建议的产品形态

**一块线索板对应一个持续的调查事项；重要线索逐步进入周围，调查报告固定在中央。** 一次调查可以跨越多轮提问、多次检索和阅读。由当前 Agent 判断新问题是在推进旧调查，还是开启独立调查。

延续现有透明悬浮操作层与后方实体场景。线索板自身仍是场景里的研究板；操作、选择、切换与阅读详情在前方轻量浮层完成。无需为了这个阶段使用 AE、Blender 或添加新的高成本渲染效果。

第一阶段的完整闭环：

1. Agent 判断沿用、新建或恢复哪块调查板。
2. 正常检索、阅读资料，发现有价值的证据后调用工具写入短线索。
3. 有新证据时补充、归并或修正已有线索，按需要建立关系。
4. Agent 发布报告，中央显示报告摘要与阅读全文入口。
5. 用户切换历史调查板，查看线索、原文和报告；追问可以继续原来的板。

后续“板旁待梳理资料区”和“手动把检索阵列资料放进档案架”先预留数据关系，不在本阶段增加这两个流程。现有用户手动编辑、拖放、连线能力保留。

## 3. 调查事项、轮次与线索的关系

建议的数据层级：

```text
Harness 会话
  ├─ 调查板 A：黑蛇与塔露拉的赌注
  │    ├─ 调查运行 1 → 搜索 / 阅读 / 线索更新 → 报告 v1
  │    ├─ 调查运行 2 → 补证 / 修正 → 报告 v2
  │    ├─ 线索 + 关系 + 来源定位
  │    └─ 用户布局与编辑记录
  └─ 调查板 B：哥伦比亚的能源体系
       └─ 另一组运行、线索与报告
```

`sessionId` 是会话；`boardId` 是长期调查事项；`runId` 标识某次执行。现有 `investigationId` 用来识别当前轮，不能直接作为 boardId。

建议第一阶段允许同一会话多板，跨重启恢复。跨会话浏览仍可通过会话入口进入；暂不自动跨会话合并调查。数据中保留 originSessionId 和 forkedFromBoardId，避免以后靠标题猜归属。

### LLM 如何判断沿用或新建

输入是用户的新问题、当前板的目标/范围/未解问题，以及历史板的简短目录。判断依据是调查目标是否连续，不是关键词数量、消息数量或时间间隔。

| 新问题示例 | 建议判断 |
| --- | --- |
| 首次询问“黑蛇和塔露拉的赌注，以及两人的后续” | 新建一个调查事项 |
| “她后来怎么摆脱影响？” | 沿用原板，补充该调查的后续 |
| “你这个判断的原文在哪？” | 沿用原板补证，必要时修订结论 |
| “把刚才报告说得简单一点” | 读取已有报告回答；不因改写自动开新板或新一轮调查 |
| “再查一下哥伦比亚的能源体系” | 新建独立板 |
| “回到刚才黑蛇的问题” | 恢复历史板 A |
| “同样是塔露拉，另开一项研究她的组织关系” | 尊重用户明确要求，新建板；人物相同也不强行合并 |
| “继续”“还有呢” | 结合最近调查目标继续；确实有多个同样合理的指代时才简短澄清 |

由当前主 Agent 直接决定，不额外增加一个隐藏的分类模型调用。代码只检查所选板是否存在、是否属于当前作用域以及参数是否完整。工具记录一句简短、可显示的归属说明，不要求输出内部推理过程。

用户明确指定“另开一个调查”或“继续这块板”时优先遵循。UI 提供“在此板继续”和“新调查”的显式入口；普通输入仍交由 LLM 判断。当前正在观看的板不自动成为 Agent 写入目标。

## 4. 什么应该成为一张线索

一张线索围绕一个值得记住、可核对的观察或问题。板面显示短标题、核心句和来源标记；完整摘录、解释和多个出处留在详情中。

推荐内容类别：

| 类别 | 作用 | 需要保留的内容 |
| --- | --- | --- |
| 原文证据 | 关键台词、档案摘录 | 短摘录、说话人/出处、精确位置 |
| 观察或判断 | 对调查问题有帮助的归纳 | 核心判断、依据、明确的推断标记 |
| 时间节点 | 建立前后顺序 | 原文时间/相对顺序、事件、来源；未知日期不得补造 |
| 关系 | 人物、事件或组织之间的重要联系 | 双方、关系说明、来源 |
| 待解问题 | 当前证据无法回答的关键疑点 | 问题、缺口、建议继续查的方向 |
| 矛盾或反证 | 两条资料相互冲突，或有证据反驳判断 | 两侧证据、差异、仍未解决的部分 |

Agent 不把每一个搜索命中自动上板。建议在读到关键原文、找到反证、厘清时间顺序、发现证据缺口时更新；连续读几份资料后可以一次写入一小批线索，不机械地规定每次工具返回都必须产出卡片。

### “别重复”的两个含义

**内容去重：** 同一判断补充新来源时更新原线索。同一篇文档里的不同判断允许成为不同线索。语义是否相同由 LLM 判断；调用重试、同一个操作重复投递由代码保证幂等。正文相似度或 sourceId 不能替代这个判断。

**视觉去重：** 不把所有内容都画成同一张大纸。以内容类型决定版式，再在有限的纸边、固定件、编号位置、细微倾角中分配稳定变体。样式在创建时确定并保存，更新文字或重新加载时不重新随机。

来源状态和判断性质分开：

- 搜索摘要可作为“待核验线索”，标清只有摘要；不能宣称读完了全文。
- 成功读到的原文记录读取范围；web_fetch 截断也明确标示。
- “已读”是工具执行事实，不代表这条来源已经证明了 LLM 的判断。
- 推断、未解决、已撤回有明确状态；旧判断被推翻后保留历史和反证关系，不悄悄抹掉。

## 5. 板面与卡片设计

### 总体构图

中央从开始就保留报告位置，避免报告生成时把整板线索推开。调查中显示目标、当前已确定的要点和未解问题；发布后换成报告封面与摘要。正文使用现有阅读器展开，不把长篇报告压进 3D 纹理。

```text
调查标题 / 状态 / 调查板切换                         最近更新

  原文短笺       时间细条             关系索引
       ╲           │                   ╱
  关键观察 ── [ 调查报告 / 摘要 / 阅读全文 ] ── 关键反证
       ╱                               ╲
  来源摘录       未解问题              对照卡

线索数量 / 来源数量                     查看其余线索
```

这只是结构示意，不意味着每条线索都必须连到中央。只画有意义的关系，选中时再突出相关连线。调查板切换放在板的标题区域，不把每块历史板塞进全局主导航，也不另铺满屏侧栏。

### 缩小默认尺寸

当前普通 note 大约为 2.8 × 1.8 世界单位，source 为 2.72 × 3.04。建议普通线索先试原来宽高的 **70%–75%**；高大的 source 模板改成短笺，额外原文进入详情。中央报告保留较大面积。

不能只统一设置 `scale = 0.7`：那会把文字一起缩到更难看清。需要重排卡片内容层级，板面先保留短标题、一个核心句和一个来源标记，聚焦后再展示更多摘要。窄视口提供同一组线索的列表入口。

原型尺寸建议：普通短笺约 2.0–2.2 × 1.2–1.5；时间条约 2.5 × 0.65–0.8；对照卡略宽；中央报告约 4.4 × 3.2。实际需根据板面投影尺寸、中文标题和当前镜头实测调整。验收看默认视图的可读性，不只看世界单位。

### 有共同风格的不同款式

| 内容 | 推荐款式 | 主要差异 |
| --- | --- | --- |
| 原文证据 | 米白窄摘录纸 | 引号/原文行标记、轻纸边、小来源脚注 |
| 观察判断 | 横向研究索引卡 | 大一点的核心句、短编号、推断/观察标记 |
| 时间节点 | 细长时间条 | 时间突出，事件在一侧；未知时间使用相对顺序 |
| 关系 | 双端关系签 | 两端名称与关系短语，避免大块正文 |
| 待解问题 | 淡灰描图纸便签 | 轻薄边框、缺口提示，透明度仍保证文字可读 |
| 矛盾反证 | 双栏对照卡 | 左右两条依据，少量暗红标记冲突点 |

统一米白、灰、墨色与现有莱茵生命细节，少量橄榄绿/暗红承担状态含义。不同类别各有少量结构变体，相邻卡片尽量不使用完全相同的变体。有限模板可以重复，但不要相邻同款、同角度、同信息密度；不承诺无限生成独一无二的装饰。

Agent 选择内容类别和重要程度，程序选择具体样式、坐标、字号与轻微倾角。用户手工调过位置、大小或样式后保存锁定标记，Agent 补充内容时不覆盖这些安排。

### 容量与动态效果

- 首轮原型保留接近现有的 **12 张主线索 + 1 张中央报告** 展示预算，先缩尺寸、改构图。确认当前性能档下有余量，再试 16 张；不先把 12 直接改成 100。
- 持久化层保存全部线索。更多内容通过主题折叠、线索列表或聚焦相关簇查看，不能被解析器截掉。折叠依据是重要程度和主题关联，不是静默丢弃较早内容。
- 新线索靠近相关簇，在预留空位短距离落位；建议试 220–320ms，不每次从检索阵列飞一份大模型过来。
- 更新原卡只突出变化位置；关系线在卡片落位后出现。不做整板重新洗牌，不让用户正在阅读的卡片移动。
- 批量更新、历史恢复、切换板使用批次过渡；不把几十个历史事件逐一重演。遵守已有减少动态效果设置。
- 只维护一个正在展示的 3D 板场景，历史板保留数据；局部更新卡片纹理与受影响连线，不提高用户当前性能档。

## 6. 给 Agent 的四个工具

按调查流程组织，避免暴露十几个画布 CRUD 工具。以下是提议名称和契约，不是已经注册的接口。

| 工具 | 主要输入 | 行为及返回 |
| --- | --- | --- |
| `investigation_get` | 可选 boardId、目录 query/cursor、所需 section | 无 boardId 时返回当前会话板目录；有 ID 时读取目标、线索摘要、未解问题或指定报告。返回标题与短 ID，避免每次把全部正文塞进上下文 |
| `investigation_open` | mode: new/resume；新板 title/objective，或已有 boardId；简短 reason | 明确建立本次 run 与板的绑定。返回 boardId/runId/revision 和当前要点。不会强制切换用户视角 |
| `investigation_update` | boardId、runId、expectedRevision、线索变更、关系变更、未解问题 | 一个小批次原子保存；可新增、补充、归并、撤回。返回创建/更新 ID、revision、冲突或来源问题；不返回整板全文 |
| `investigation_publish` | boardId、runId、expectedRevision、标题/摘要/报告 Markdown、引用 | 原子发布该板的新报告版本，返回版本 ID 和可打开入口。保留旧版，不从会话最后一句话猜完成 |

契约约束：

1. sessionId 从真实的执行上下文获得，不由模型自由指定。每次写入显式携带 boardId/runId，检查绑定关系，避免迟到的并行结果写到新板。
2. `investigation_open(new)` 以真实调用身份保证重试不重复建板；重复调用使用已有 run/board 时有明确结果。语义相近但不同调用是否应合并，仍由 LLM 判断。
3. 新线索可以用批次内 clientKey 建立同批关系，工具返回稳定 clueId 映射；修改已有线索必须使用真实 ID。归并保留旧 ID 到新 ID 的引用映射，旧报告仍可追溯。
4. 工具以当前 DSH 支持的 JSON schema 子集声明，不依赖未经验证的复杂联合类型。字段互斥、长度、来源范围和关系完整性在服务端逐项校验。
5. 写入工具使用互斥执行；后端仍负责处理用户与 Agent 同时写入。只读工具可以在符合 Host 约定时并发。
6. 每次成功返回以持久化完成为前提。幂等凭据与变更同一次提交，取消和失败不返回虚假成功。重放 UI、`presentCall`、`presentResult` 都不得产生写入。
7. LLM 不提供像素坐标、纹理地址或布局算法参数。工具为“研究”服务，画布操作留给程序与用户。

调用节奏示意：

```text
get（必要时查历史目录）
→ open（沿用或新建，锁定本次写入归属）
→ 原有检索/阅读工具
→ update（关键线索，可小批次）
→ 继续阅读 / 对照 / update
→ publish（报告 v1）
→ 在会话中给用户结果说明和报告入口
```

报告正文以板上的报告实体为权威版本。会话可显示同一份报告的投影，或给摘要与入口；不要求模型在 publish 参数里写完全文后，又在最终回答里重新生成一份不同的全文。

## 7. Skill 设计

建议新增独立的项目内 skill `prts-investigation`，与现有 `prts-retrieval` 配合。它属于这个 Harness 插件，不是装到 Codex 个人目录里的 skill。

现有 skill 负责“怎么检索、怎么读原文、怎么回答”；新 skill 负责“如何把研究组织成持续调查、何时记录线索、如何发布报告”。在 PRTS preset 注册，现有检索 skill 的发现描述/正文只加入简短的协作入口，不把全部板规则拼进所有检索配方。

建议结构：

```text
skills/prts-investigation/
  SKILL.md
  references/
    routing-examples.md     # 新建、追问、切回历史板、范围变化
    evidence-examples.md    # 好线索、重复归并、摘要与全文、反证
    report-contract.md      # 报告组织、引用、版本、未解问题
```

主文控制在约 120–180 行内，详细例子按需读。核心规则草案：

> 处理需要检索、核验、比较或整理的调查时，先检查当前调查目标及相关历史板。根据用户目标决定继续、恢复或新建；新的一轮用户消息本身不是新建理由。
>
> 阅读后记录能够改变答案、支持关键判断或指出证据缺口的线索。同一判断优先补充现有线索，保留出处与不确定性。不要为了让板看起来丰富而把所有命中或尚未发生的结论写上板。
>
> 在有意义的新发现后更新板，不等到全部回答完才补一块静态板。允许合并小批次更新，避免逐句或逐段刷工具。
>
> 发布报告前核对结论与来源、保留反证和未解问题。继续旧调查时更新该板并发布新版本，保留已有报告。工具失败时如实说明保存未完成。

动态上下文只给当前 board/run、调查目标、最新版本、关键线索摘要与少量相关历史板；完整内容通过 get 按需读。目录 query 是发现候选的手段，最终归属仍由模型判断，不能把“候选没返回”机械等同于“应该新建”。

## 8. 存储、同步与来源

### 使用当前 Host 的能力

核对的构建源为 `prts-terrarchive-portable/.build/dsh-electron`，版本 `0.1.5-alpha.1`，commit `5dda764ed3aa172535a7967b06ff95d9cbfe536a`。

其默认 `packages/bundle/base/cordis.patch.yml:144` 已包含 storage、storage-json、storage-domain。`ctx.storageDomain` 支持领域内串行更新和落盘后 `domain/changed` 通知，适合非聊天记录的应用状态。

建议新增一个 **Host 级单例调查服务**，由 UI 和 Agent 工具共同使用。该服务只打开一次同名领域，不能让每个 Agent 插件实例各自打开同名存储。普通资料检索入口继续独立加载。

第一版建议按会话打开一个领域，安全名称由会话 ID 派生；使用 JSON 的 `single` 布局，保存一个包含多块板的会话调查集合。这样板内容、报告、run 绑定和幂等凭据可以一次原子写入。领域只在需要时打开并由 Host 管理生命周期，其他会话不必全部常驻。

这是有意识的初期取舍：每次提交会重写该会话的数据文件，因此只在小批次变更或编辑提交时写入，不逐字保存、不逐帧保存拖动。大量历史报告下需要测量写入耗时与文件体积，再决定是否改用 SQLite 后端或更细的数据分区。

**不能直接照抄 Host 的缓存存储方式：** 当前 JSON `per-record` 实现会将部分损坏、不可读或不接受的版本记录视为不存在；它不能未经额外保护就作为用户线索板的权威存储。`single` 布局读取错误显式失败。升级需备份并显式迁移，不依赖静默丢弃旧数据。

当前领域层没有跨表事务；`update` 内完成一次不可变变换。工具输入和生成的新记录都在调查服务校验，不能仅依赖 TypeScript 类型或 README 的概括：当前 `KvTableImpl.put/update` 没有逐次执行应用记录 schema 校验。

依赖处理放到独立服务入口：显式声明并验证所用的 Host storage-domain 接口和 schema 库依赖，不假设 pnpm 工作区能解析就等于发行包能解析。测试构建的打包审计必须验证这个入口及 skill 文件可独立加载。

### 最小数据对象

```text
InvestigationPortfolio
  schemaVersion, sessionId, commitSeq
  boards, runBindings, appliedMutationReceipts

InvestigationBoard
  id, title, objective, scope, createdAt, updatedAt
  knowledgeRevision, layoutRevision
  clues, relations, sourceRefs, reports, openQuestions

Clue
  id, kind, title, summary, detail, importance
  evidenceRefs[], interpretation: observation | inference | question
  status: active | unresolved | superseded | retracted
  authoredBy, contentRevision
  visualVariant, styleSeed, position, scale, userLayoutLocked

SourceRef
  origin, title, sourceId, documentUid/sourceRef 或 URL
  dataVersion, 行范围/段落锚点, excerpt, contentHash
  readReceiptId, returnedAt, truncated, availability

Relation
  id, fromClueId, toClueId, type, label
  type: supports | contradicts | precedes | relates

ReportVersion
  id, title, summary, markdown, citations
  basisKnowledgeRevision, publishedAt, runId
```

摘要中的原文片段需要保留快照；本地资料升级或网页变更后仍可解释当时依据。来源全文按现有资料管理方式读取，调查集合只保留必要短片段和定位，不重复复制每篇全文。

单靠来源 ID 存在只能证明“有这份资料”。工具记录的读取凭据才能证明返回过哪些内容；语义是否支持结论仍属于研究判断。web_search 摘要、web_fetch 正文、工具错误以及 PTC 嵌套调用都要有各自的结构化适配，不能靠前端状态条里的中文文本猜。

### 版本与冲突

- commitSeq 随每次持久化提交增长，用于 UI 同步与去重。
- knowledgeRevision 仅在调查内容变化时增长，报告记录其依据版本；用户移动卡片不把报告变成过期。
- Agent 写入声明 expectedRevision（对应 knowledgeRevision）。内容冲突返回当前版本与冲突线索，让 Agent 重读相关部分后再补丁更新，不覆盖整板。
- 用户修改过的正文保留作者与版本。Agent 不静默覆盖用户文本，可追加自己的观察或返回冲突；用户布局由独立 layoutRevision 管理。
- 原来保存整板快照的撤销方式需改为用户操作的逆向补丁。撤销自己的一次拖动不应撤销期间 Agent 新增的三条线索。

### 同步与视角

用户的 viewedBoardId 与 Agent 当前 run 的 workingBoardId 分开。后台更新另一块板时，在目录上显示“新增 2 条”，用户可选择查看；不强制换板、拉镜头或弹报告。

Host 的 domain/changed 只是进程内事件。由调查服务通过现有已认证 Connection/Remote 通道暴露板快照与订阅；浏览器、Electron 都使用同一份契约。断线重连、订阅建立和切换会话时按 commitSeq 补快照，不能认为前端一定收到每个通知。

报告成功发布即成为可阅读的持久对象；执行是否正常结束另取真实 run 终止状态。发布前中断保留线索与旧报告，显示本次未完成；发布后中断不撤销已经保存的报告。新证据到来而尚未发新版时，旧报告标记“有新线索，待更新”。

## 9. 与后续资料区的衔接

| 空间 | 用户提出的定位 | 建议的数据含义 |
| --- | --- | --- |
| 检索阵列 | 可以发现、浏览和选择的资料 | 检索结果/资料目录 |
| 档案架 | Agent 阅读过的资料；后续允许用户手动收录 | 阅读凭据 + 用户收藏，分别标明来源 |
| 板旁新区域（名称暂定“待梳理资料”） | Agent 认为值得仔细梳理，或用户手动加入 | 附属于某个 boardId 的资料队列，不等于已形成线索 |
| 线索板 | 提炼后的重要观察、证据、问题与关系 | 调查知识记录 |
| 中央报告 | 当前调查的综合答复 | 有版本、可追溯的报告 |

同一资料可以“已读”“待梳理”“被多条线索引用”同时成立，不能用一个互斥枚举表示。现在档案架仍包含一些 found 来源，并非完全符合未来“Agent 已读”的定义；本阶段先记录正确的阅读与引用事实，后续再调整收录行为和新区域 UI。

现有手动钉到板上的入口可以继续保留，新增内容明确标为用户添加，未核验时不自动成为 Agent 已确认的结论。

## 10. 落地顺序与验收

### A. 先验证尺寸与版式

用明确标为测试数据的一块调查板，验证缩小的六类线索、中央报告、长中文标题、密集关系及窄窗口。确定当前镜头下哪些文字能直接读、哪些需要聚焦。只保留有用途的款式。

### B. 接通持久化与工具

建立 Host 调查服务、四个工具、报告对象和来源凭据；用结构化测试数据跑通新增、补证、归并、重试、重启恢复、用户编辑冲突。此时前端可以先用简单列表检查权威状态，避免画面掩盖数据错误。

### C. 接入 skill 与实时板面

加入 LLM 路由判断，按真实工具提交增量更新 3D 卡片；连接报告入口和多板切换；保留前端用户的查看位置。真实新板为空，旧 localStorage 数据仅做一次可恢复迁移。

迁移时通过已知示例身份与内容识别未编辑演示数据；不能只凭标题像示例就删除。用户改过的内容保留。迁移成功且收到后端确认后再写迁移标记，旧数据留作备份。

### D. 场景验收与测试构建

| 验收场景 | 必须满足 |
| --- | --- |
| 同一主题连续追问三次 | 一块板、多个 run，必要时多个报告版本 |
| 同一人物换独立研究目标 | 能新开板，不因人名一致强行合并 |
| 中途切换主题，再回到旧问题 | 正确选板，旧报告与线索仍在 |
| 仅要求改写已有回答 | 不机械创建新板/新调查 |
| 20 条搜索命中，读到 3 条关键证据 | Agent 选择重要内容上板，不按命中数制造卡片 |
| 一条判断获得第二份出处 | 原线索补证；同篇资料中的另一条判断可以另建 |
| web_search / 成功或失败的 web_fetch / 截断正文 | 摘要、已读、失败状态准确，来源能打开；不虚构已阅读全文 |
| 工具重试、PTC、UI 历史回放、重连 | 不重复建板、不重复钉卡、不重演全部入场动画 |
| 用户正在看旧板，Agent 更新新板 | 只给提示，不抢用户视角 |
| 用户拖卡/改文时 Agent 新增线索 | 两边内容都保留；撤销用户操作不抹掉 Agent 更新 |
| 报告发布前中断、发布后中断 | 准确显示执行结果，已保存报告与线索不丢失 |
| 超过场景展示数量、重启应用 | 全部数据仍在，折叠内容可访问 |
| 当前性能档下快速连续更新 | 只重绘变化卡片；未展示板不新增 3D 场景；无整板闪动 |
| 测试发行版脱离源码目录启动 | 新工具、服务、skill 和来源阅读均能加载 |

LLM 路由质量需要用用户式多轮样例验证，不能只靠单元测试证明。建议准备约 20 组路由样例和 8 组完整调查样例，留一部分不参与提示词调整；记录错误新建、错误合并、重复线索、漏存报告、额外工具耗时与 token 成本。本轮未运行模型评测，尚不能声称某个提示词已有稳定命中率。

本阶段验收后再使用现有未压缩测试发行版流程交付。工具/存储先闭环，后续资料队列便可复用 boardId、SourceRef 和阅读凭据。
