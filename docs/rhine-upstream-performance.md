# 当前插件与真正原版的性能对照

2026-09-12。对照源是 `/home/cloudstack/ai-data/RhineLabUI/src/scene.ts`，不是插件早先的构建。本轮只评估并保存证据，没有修改产品代码或重新发布。

> 后续已按用户决定移除画质选择，统一到本文画质 A 对应的性能参数；档案架保留透射 1。本文保留收拢前的完整对照数据与默认值说明，当前行为见 [固定性能画质](rhine-performance-only.md)。

当前阵列总览的几何提交量比原版少约 13%～15%，抽出特写少约 60%～62%，绘制调用则略多。首次加载、纹理常驻量、档案架及宿主业务仍有额外成本，不能概括成整个插件比原版更轻，也不能把几何降幅换算成 FPS 提升。

## 对照方法与边界

- 直接将两边当前的 `ArchiveScene` 编译为临时测量入口；esbuild 参数一致，实际加载的 Three.js 都是 0.183.2，核心文件哈希一致。GLB 分别从各自目录读取，内容哈希也一致。
- Chromium，1280×720 CSS 视口，DPR 1，baseline 灯光。分别强制相同的画质参数；不是直接选择两边名称相同但设置不同的“性能”预设。
- 每个视角推进 200 个状态帧收束相机，期间禁用 Composer 绘制。随后恢复三个完整实际绘制帧，三个帧的提交量完全一致。中间状态推进不计为渲染性能样本。
- 自动断言双方的相机位置、朝向、FOV、模型姿态、选中槽、渲染尺寸和画质参数相同，全部通过；没有页面或 Console 错误。
- 这是独立三维核心的静止末端对照。没有加载宿主、业务 UI、字体、档案架、运输或检索，也没有测抽取过程的帧时间。原版磨砂外观与插件清晰盖板、烘焙内构的呈现不同，因此是各自实际实现的成本比较，不是完全相同画面的优化实验。
- 环境没有 `/dev/dri`，实际适配器为 ANGLE / SwiftShader。记录中的初始化与提交耗时仅供排查，不作为硬件 GPU 时间、真实启动速度或 FPS 结论；不同画质共用 Context，后续程序数和纹理计数也含缓存。

画质 A：100% 渲染比例、DPR 上限 1、SMAA、1024 阴影、AO 0、景深 0、透射分辨率 0.5、各向异性 4。等于插件当前性能参数。

画质 B：100%、DPR 上限 1.5、无 SMAA、2048 阴影、AO 32 / 全分辨率、景深 100、透射 1、各向异性 16。等于两边“原始”预设；本机 DPR 1，实际输出仍是 1280×720。

## 实际绘制结果

“帧三角形”包含主画面、透射、阴影、AO、景深及全屏处理的重复提交，不是模型的唯一面数。

| 相同条件 | 原版帧三角形 | 插件帧三角形 | 减少 | draw calls：原版 → 插件 |
| --- | ---: | ---: | ---: | ---: |
| A：阵列总览 | 2,638,234 | 2,299,502 | 12.84% | 51 → 55 |
| A：抽出特写 | 2,638,234 | 1,051,682 | 60.14% | 51 → 55 |
| B：阵列总览 | 5,330,799 | 4,544,859 | 14.74% | 102 → 106 |
| B：抽出特写 | 5,330,799 | 2,049,219 | 61.56% | 102 → 106 |

原版每个批次始终提交 288 个槽，选中槽用缩零隐藏；镜头缩近后普通阵列提交量不下降。插件总览提交 166 份非投影实例，特写提交 61 份；投影背板保留 287 份，避免画外阴影突然消失。开启 AO / 景深时，投影对象回调由每帧 6 次降至 2 次，对应同帧阴影复用；回调数本身不是 GPU 通道数。

总览收益较小，是因为插件也增加了阵列细节。真正原版只实例化盖板、边框、螺丝、镶片和背板：**5 批，每份 4,200 三角形**。插件默认增加烘焙内构平面与保留的外侧细字：**7 批，每份 6,130 三角形，增加约 46%**。视野裁剪抵消了这部分成本，并在特写时产生更大的净收益。

此前记录的 **23,556 → 6,130** 是“插件加入完整内构后，再改用烘焙”的阶段对照；原版普通阵列本来就不提交那些完整内构，不能把该阶段降幅称为相对原版提升。原版和插件都保留完整抽出模型，其实体几何为 82,346 三角形，另有名牌平面。

## 首次加载和内存

| 项目 | 对照结果 |
| --- | --- |
| cassette GLB | 两边相同，3,565,116 字节 |
| assembly GLB | 两边相同，3,343,744 字节，按查看器需求加载 |
| MiSans 字体 | 四份文件逐一相同，共 19,744,460 字节；Regular + Bold 共 9,939,728 字节 |
| 插件内构贴图 | 每次创建场景现场烘焙一次并同步读回；1024×740，CPU 像素数据约 5.78 MiB，GPU HalfFloat 纹理含 mip 理论约 7.71 MiB |
| 十二份架上名牌 | 各自独立 1024×440 RGBA8 纹理，含 mip 理论共约 27.50 MiB |
| 三份启动活动模型预备 | 共享几何，但独立标签理论再增加约 6.87 MiB 纹理 |

以上纹理量按尺寸和格式计算，不是浏览器实测 VRAM；未含 Canvas 后备存储、临时渲染目标、驱动对齐和材质开销。内构图由所有阵列实例共享，也不是 288 张图。模型几何仍完整加载：仅实体属性和索引的理论数据量约 3.23 MiB，架上盒子共享它，不是把它再复制十二份。

烘焙当前没有减少 GLB 下载、完整模型解析或源几何保留；额外增加一次启动渲染和同步读取。它属于运行时替代内构的措施，尚未成为离线生成、随资源包加载的压缩纹理。

现存构建快照中，JS + CSS 原始总字节为原版 962,162、插件 1,153,142；使用 Python gzip level 9 本地估算后分别为 288,682、332,186，增加约 43.5 KB / 15.1%。这不是本轮统一重建的包体，也不是实测 HTTP 传输量；原版 PWA 缓存与 DSH 宿主成本未纳入。

## 业务场景与画质取舍

原版没有十二份档案架及检索资料运输，无法给出对应的原版 FPS 对照。插件架上模型仍为完整实体，每盒 16 个实体 Mesh、名牌和状态标记分别绘制。十二盒仅实体几何一次完整遍历约 98.8 万三角形，实际整帧还需考虑多个渲染通道。这是下一阶段值得优化的独立成本。

分帧准备、活动与架上模型缓存已经实施，减少了动画时集中分配，但缓存本身占用常驻资源。此前同一插件十二份新资料到达的同步更新诊断为 42.2 → 8.3 ms，见 [检索卡顿记录](rhine-search-stutter.md)；这不是与原版检索功能的对照，也不是当前硬件端 FPS 实测。首次进入架上场景曾记录到两个新 Shader Program 和一次编译相关尖峰，当前标签预热没有覆盖全部材质编译。

插件依然每帧计算 288 个逻辑槽的运动，并额外做包围盒裁剪和提交压缩。现有证据支持减少 GPU 无用几何提交，不支持声称 CPU 动画计算同比减少。前台仍持续运行三维帧循环，标签页隐藏和查看器打开时会暂停主场景。

“性能”预设已经从原版 80% / 无 SMAA，提高为插件 100% / SMAA。在不触发尺寸上限时，主画面像素量增加 **56.25%**，另增加抗锯齿处理。因此几何减少不保证同名档位帧率一定提高。插件无存储偏好时的默认值也采用 DPR 上限 2 和 SMAA，原版默认为 DPR 上限 1.5、无 SMAA；高 DPI 屏幕需另看实际输出尺寸。

最近为了架上清晰度，将该视图透射分辨率固定为 1、关闭景深。对于此前透射 0.5 的性能档，透射捕获像素量理论变为四倍；这是局部清晰度成本，不是整个主画布扩大四倍。高画质档则同时省去了架上景深处理，详见 [档案架清晰度](rhine-shelf-clarity.md)。

## 下一步建议

1. 针对首次抽取、入架卡顿，先覆盖实际材质的着色器预热，并继续测新资料更新和纹理上传尖峰。
2. 架上静止盒子使用合批或分级模型，只为选中、抽出与首尾露面部分保留必要细节；保留清晰盖板下可见的内构和边沿。
3. 复用名牌公共品牌图，将可变编号单独处理，减少十二张完整名牌的重复像素和绘制状态。
4. 将内构现场烘焙迁到离线资产流程，再评估纹理格式和完整模型延迟加载。已有资源文件并未压缩，需同时验证颜色、清晰边缘与加载过渡。

真正的体感结论仍需目标电脑浏览器硬件加速下，在相同实际渲染尺寸进行持续滚动、抽取和检索的帧时间 / 尖峰对照。本轮不据软件渲染器给出 FPS 加速倍数。
