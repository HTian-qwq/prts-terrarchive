### 阵列

逻辑窗口固定为 9 × 32 = 288 个槽位，已经使用 `InstancedMesh`，无需再从零实现实例化。当前插件按 8 个材质组提交阵列，单份 **23,556 三角形**，单次完整遍历为 **6,784,128 三角形**。Three.js 对缩放为零的实例仍会执行实例绘制，不能把这种隐藏方式计为剔除。

与当前上游实现相比，插件阵列增加了 `Internal_Ceramic`、`Subsurface_Optics`、`Optical_Edges` 三组内构，合计每份 19,356 个三角形。这是保留完整内构的视觉定制，也是背景 LOD 最有价值的入口。优化必须保留这些结构在当前透明外壳中的可见效果。

其中 `Optical_Edges` 占阵列面数约 47.4%，应优先检查环组细分与小孔的环形几何；不要只盯着完整单体中最大的材质组。

依据：[`archive-loop.ts`](../ui/rhine/original/archive-loop.ts)、[`original/scene.ts`](../ui/rhine/original/scene.ts) 的 `shellSurfaces`、`bodySurfaces` 与实例创建逻辑。每个实例组目前 `frustumCulled = false`；切到档案架时主要移动相机并显示架上模型，阵列仍更新和提交。可以保留 288 个逻辑槽位，仅压紧当前真正需要绘制的实例列表。

### 同一几何会经过多个通道

当前主场景有主画面、透射背景捕获、SSAO 法线 / 深度、景深深度，以及为清晰文字新增的高分辨率遮挡深度。玻璃的双面绘制和阴影还会产生额外提交。`renderer.info.autoReset = false`，每次场景更新在 composer 前清零，随后累计 composer 与文字通道，因此 `stats().renderedTriangles` 是**一帧所有通道的三角形提交总量**。

已有 `/tmp/prts-rhine-measure-AvzKvq/measure.json` 记录了 34,083,654 个三角形提交。仅阵列约 678 万 × 五份几何遍历，就达到约 3392 万，可以解释该数字的主要构成；它不表示独立模型有 3400 万面。记录来自 SwiftShader，采样窗口内只有 0 帧；另一份记录也只有 0–1 帧。不能据此判定硬件 FPS、AO 收益比例或优化后的速度。

已确认两处可单独验证的重复开销：

- [`label-renderer.ts`](../ui/rhine/original/label-renderer.ts) 在最终画布上清深度，用 `overrideMaterial` 重画整个 layer 0，再画标签。它已经关闭该通道的阴影刷新，但仍提交复杂阵列几何。
- 主画面、SSAO 与 Bokeh 的场景渲染没有统一冻结阴影更新。当前 Three.js r183 源码中，这几次 `renderer.render()` 都会进入自动阴影更新。可以让阴影每个逻辑帧更新一次，继续保留运动投影。

现有画质为 `WORKBENCH_QUALITY`：景深 100、32 样本 AO、2048 阴影、SMAA、最高 2 倍像素比。复杂通道已有约 830 万像素上限。清晰标签即使在设备 DPR 为 1 时也请求 2 倍目标，结合舞台缩放后，同样受像素上限与最大纹理尺寸约束；最终输出取标签和 composer 需求中较高的倍率。因此主画面降采样后，标签深度仍可能很贵。`docs/rhine-lab.md` 关于降低景深、档案架关闭景深的文字已与当前代码不符，应以 `scene.ts` 为准。

## 烘焙什么，保留什么

| 部位 / 效果 | 推荐处理 | 视觉验证重点 |
| --- | --- | --- |
| 螺丝槽、细刻线、密集肋条、微小倒角 | 低模承载法线、局部 AO、粗糙度；必要时基础色 | 斜视轮廓、掠射高光与接缝；轮廓显著处留几何 |
| 内构两环及连接带 | 先降低环向分段、保留大轮廓；远景再试低模 + 烘焙内构 | 阵列透明壳内仍能读出两环，近景不能变成平面印花 |
| 外壳厚度、周边轮廓、黄色顶边嵌块 | 保留简化后的真实几何 | 抽取侧面、卡片间隙、黄色块齐平关系 |
| 磨砂到清晰的移动揭示、折射、视角相关反光 | 近景保留当前运行时材质与 shader | 相机转动和解密时连续，禁止烘死为一张正面图 |
| 动态标题、档案编号、状态 | 独立动态标签；按投影尺寸分配纹理 | 中文可读、内容实时更新，不写死进美术贴图 |
| 单个零件自身的遮蔽 | 可烘焙局部 AO | 拆解后仍合理 |
| 卡片彼此、卡片与地面、拆解零件之间的遮蔽 | 保留动态阴影 / 必要的屏幕空间 AO | 抬升、波浪、抽取、拆解不能留下固定黑影 |

烘焙要替代原来的小几何或实时计算才有性能收益。仅给原高模添加法线 / AO，反而增加纹理取样和显存。烘焙 AO 也不能直接等同于关闭全部 SSAO：前者适合固定局部关系，后者还表现运动物体的接触关系。

现有 UV 不足以直接开始整模型烘焙：cassette 只有 14/17 个 primitive 带 UV0，assembly 为 16/22。前者 `Optical_Film_Edge` 中有 7,680 个 UV 退化三角形，另有 27,017 个完全重叠 UV 三角形的额外副本。应重新展开和打包低模，不能把“存在 UV”当作“烘焙就绪”。此外 `appearance.ts` 的盖板揭示 shader 在读取粗糙度图后重新赋值 `roughnessFactor`；直接挂粗糙度贴图会被覆盖，必须设计贴图与揭示的合成方式。

建议先制作一个可比对的低模样本：保留高模作投射源，给低模重新整理可烘焙 UV，生成切线空间法线与局部 AO；粗糙度 / 金属度保持当前基线，需要时打包为 ORM。基础色使用 sRGB，法线和 ORM 按非颜色数据处理。共享同一套静态图集，先比较 1K 与 2K；只有可见纹理细节要求更高时才增大。Blender 的烘焙需要 UV 与指定输出目标，支持从选中的高模投射到活动低模。[Blender 烘焙手册](https://docs.blender.org/manual/id/4.4/render/cycles/baking.html)

物理玻璃本身仍有较高的逐像素成本；背景几何 LOD 完成后，再比较远景材质简化和透射缓冲分辨率，分别记录收益与失真。[Three.js MeshPhysicalMaterial](https://threejs.org/docs/pages/MeshPhysicalMaterial.html)

## LOD 的具体组织

建议按**使用状态 + 屏幕投影尺寸**选档，而不是只比较相机距离。当前是长焦镜头，FOV、视口比例与详情构图都会变化，同一距离不保证同一屏幕大小。Three.js 内置 LOD 按距离切换并支持迟滞，可作为参考；本项目更适合自己把实例分配到少量共享的 LOD 批次。[Three.js LOD](https://threejs.org/docs/pages/LOD.html)

| 使用状态 | 资源与绘制建议 | 第一轮试验预算² |
| --- | --- | --- |
| 选中、正在抽取 / 归位、查看器 | 保留当前完整模型与材质，先建立视觉基线；后续替换微细节 | 初期保留当前约 8.2 万实际主体三角形 |
| 前排较大的背景卡、架上文件 | 保留简化两环与外壳，细节用共享贴图；阵列继续分批实例化，资料架另评估合批，动态标签独立 | 每份 4,000–8,000 三角形 |
| 后排 / 小投影卡片 | 简单外壳与内构代理，可试烘焙内构图层 | 每份 500–2,000 三角形 |
| 相机外且不贡献画面、阴影或透射的槽位 | 不加入当前绘制实例列表 | 0 个提交实例 |

² 是原型目标，不是测量结果或保真承诺。先比较视觉，再确定预算，不强迫所有零件达到固定简化百分比。

实现要点：

1. 保留当前逻辑槽位、选档记忆、波浪和抽取坐标。另维护 `instanceId → logical cell` 映射，压紧 LOD 批次后拾取仍回到正确档案。
2. 同一循环中快速重选、旧卡片归位、最多两个 Agent 运动文件，都保留当前运动状态。高精度资源在动作开始前准备，不能在第一次抽取时才阻塞下载或编译。
3. 在抽取前升级、归位收束后降级，加入迟滞。外壳尽量共享几何和材质连续性，避免同时叠两层透明壳做普通透明淡变。几何、阴影、深度代理同步切换。
4. 摄像机视锥、透射取样边缘、阴影投射范围、波浪最高点与运动余量都要进入保守剔除范围。不能仅因一个物体当前在画面外就忽略其阴影贡献。
5. 阵列用少量按材质 / LOD / 空间块组织的 `InstancedMesh`；不为 288 份档案各建一整套独立 LOD 树。减少三角形时也控制 draw call 增长。

简化工具可用 glTF Transform / meshoptimizer，但要按材质和部件指定误差，保护薄片、硬边、UV 接缝。其目标 ratio 受误差阈值和拓扑约束，不是保证结果；合并前先确认材质和拆解语义。[glTF Transform simplify](https://gltf-transform.dev/modules/functions/functions/simplify)

## 推荐执行顺序

### 根据用户阵列截图细化：优先按露出高度选择几何

用户随后提供的阵列截图显示，密集区域主要露出顶边与一小段正面；列间空隙仍露出较长的侧面，选中卡片则明显高于周围。因此背景资源不必仅按距离 LOD，还可以按实际露出的区域分级。

建议离线准备“顶沿条带 / 较深上部 / 全高简化壳”几档几何，以相机投影、前方遮挡卡片及相对升降高度选择批次。波浪使前方卡片下降、后方卡片升起时，提前启用更深一档；抽取前切换完整近景模型，归位后再恢复。选择档位保留空间余量和迟滞，不逐帧重新切割高模。每一档继续批量实例化，批次中共享绘制范围；不能给同一个 `InstancedMesh` 中每张卡片独立指定 `drawRange`。

“动态遮罩”可以用于原型验证遮挡边界，但不能把 fragment clipping 的不显示等同于不提交几何。本地 Three.js 的 `clipping_planes_fragment.glsl.js` 在片元阶段使用 `discard`，完整高模的顶点与三角形提交仍然存在；真正降低几何负担应使用预切几何、正确排列的索引绘制范围或不提交对应几何批次。[Three.js clippingPlanes](https://threejs.org/docs/pages/Material.html#clippingPlanes)、[BufferGeometry drawRange](https://threejs.org/docs/pages/BufferGeometry.html#drawRange)

列缝侧面、外围卡片、通过玻璃仍可见的区域不能统一按水平线切掉。保留必要的全高低模外壳与遮挡 / 阴影代理，确保简化后的卡片还能遮住后方物体；颜色、透射、标签遮挡、AO / 景深深度及阴影所需几何分别验证。可见顶沿与上部正面的细节再用共享烘焙贴图表达。仅凭单张截图不能确定全相机运动中的安全裁切高度。

| 顺序 | 工作 | 目的与验收 |
| --- | --- | --- |
| 0 | 固定现状截图、模型散列、相机状态与真机帧时；完善测量口径 | 后续知道改了什么、哪项有效 |
| 1 | 阴影每帧只更新一次；档案架视角下保守剔除阵列；标签深度改用合适的简化遮挡代理 | 优先消除重复提交，保持当前主画面材质 |
| 2 | 制作一套背景 LOD，并与当前完整内构对照；接入共享实例批次 | 降低被多个通道重复处理的几何量 |
| 3 | 给低模烘焙微细节、局部 AO / ORM；按近景与远景决定材质等级 | 用有限纹理成本换掉细小几何和部分着色成本 |
| 4 | 标签纹理分级 / 复用，后处理代理与分辨率按实测调整 | 保留文字清晰度，控制显存与像素开销 |
| 5 | Meshopt / KTX2、字体分包、资源版本缓存、加载预热 | 改善首次打开、传输和内存；另行评价，不混作 FPS 收益 |

不要一开始就全局关闭 AO、景深或玻璃，也不建议此阶段迁移渲染引擎。先优化上述重复工作与背景资源，便于保留已定制的视觉。

## 标签、加载和工具链

- 单张动态标签目前为 2048 × 880，RGBA8 基础层约 6.88 MiB；若有完整 mip 链，约 9.17 MiB。十二槽标签理论上约 110 MiB，另有主卡、运动副本、CPU Canvas 与后处理资源。这是格式推算，不是显存测量。可根据实际投影在 512 / 1024 / 2048 宽度间分级，近景预先升级，复用 Canvas / Texture 并只在内容变化时更新。静态背景纹理与动态中文标签不必走同一压缩流程。
- 四款 MiSans WOFF2 合计 19,744,460 字节，比两份 GLB 总和约 6.91 MB 更大；`createRhineScene` 同时等待模型和 Regular / Bold 字体就绪。首次启动还应测字体传输与字体加载阻塞。中文标题是动态的，字体优化应按 Unicode 分包并保留覆盖能力，不能只取当前静态界面上出现的文字。
- 拆解模型已按需加载并缓存模板，Rhine bundle 已懒加载。无需把它们作为“尚未实现”的优化项。打开独立查看器时主场景已暂停；主场景已有页面隐藏、停用与 context lost 暂停逻辑，退出时释放资源。这不等于查看器有完全相同的隐藏恢复和 context lost 处理。可见页面的 RAF 则仍持续运行；如后续节能优化，需要明确呼吸等持续动画是否保留，不能把动效自动停止当作无视觉变化的优化。
- 两份 GLB 当前没有压缩扩展。Meshopt / Draco 首先解决传输和解码后的数据组织；不做 simplify 就不会自然减少面数。KTX2 在新增静态烘焙纹理后才有对应资源可压缩。glTF Transform 有独立的检查、简化、合并、量化、压缩工具，应该显式选择流程，不直接对原资产执行全部默认优化。[glTF Transform CLI](https://gltf-transform.dev/cli)
- 当前 `new GLTFLoader().loadAsync()` 没有接入 Meshopt 或 KTX2 解码器。KTX2 需要配置 Basis 转码资源并在加载前探测 GPU 支持；解码资源也应随插件分发。[Three.js KTX2Loader](https://threejs.org/docs/pages/KTX2Loader.html)
- 插件 `src/ui.js` 与独立预览都使用固定资源白名单。新增 LOD GLB、烘焙贴图、WASM / decoder 时，要同步打包、MIME 与资源路由，并确认实际 DSH 宿主可加载。现有资产路由为 `no-cache`，优化缓存前先引入内容版本标识，不直接给固定文件名加永久缓存。
- 源美术脚本在 RhineLabUI 的 `art/build_archive.py`、`build_assembly.py`、`internal_architecture.py`、`shell_reference_details.py` 等。制作 LOD / 烘焙时要保留独立高模和可复现脚本；拆解 GLB 保留 `assemblyPart`，运行时还按材质名称绑定外观。不能跨部件随意 join、flatten 或重命名。
- 两个 `.blend` 源工程和生成脚本已经存在，附件记录了散列；本环境 PATH 没有 `blender`，尚未执行源脚本验证重建结果。
- 来源项目 `AGENTS.md` 明确要求美术资源经 Blender MCP 制作并保留源文件 / 脚本。本会话没有可调用的 Blender MCP 工具；不妨碍本次调研，但开始资产制作前需要确认制作环境。此次没有安装工具、生成模型或触发该制作流程。

## 后续测量与验收

现有 `bin/measure-rhine.mjs`、`measure-rhine-console.js` 可复用，但需要先修正或注明以下限制：

1. 浏览器 console 脚本独立采样 RAF；场景计数没有增加时会回退到 RAF 速率。应把“场景 0 帧”单独标记，而不是当作渲染 FPS。最终完成后还应取消自身 RAF，异常时用 `finally` 恢复设置。
2. “关 SMAA”只关闭后处理 SMAA，WebGL context 仍是 `antialias: true`；“全关”仍有玻璃、最低 0.25 的透射缓冲、标签深度和输出抗锯齿。应使用准确实验名称。
3. 分辨率实验同时记录 CSS 尺寸、DPR、composer、输出画布、AO、透射及阴影尺寸；标签单独的高分辨率输出和像素上限可能使设置变化不等于成本同比变化。
4. 记录实际渲染帧间隔 P50 / P95 / P99、长帧、draw calls、每通道 submitted triangles、纹理 / 几何数与加载时间。GPU timer query 在支持时使用，处理 disjoint；RAF 间隔不是 GPU 执行时间。
5. 保持相同设备、分辨率、电源模式、画质、视角和资料量。每项变化先预热，再进行有足够渲染帧的重复测试；限制刷新率下 FPS 同为 60 不代表成本相同。

场景至少覆盖：冷启动 / 热启动、阵列静止、连续横纵循环、波浪和快速重选、抽取 / 揭示 / 归位、最多两个 Agent 运动文件、十二槽档案架与分页、相机往返、独立模型旋转 / 拆解，以及隐藏后恢复。视口覆盖 16:9、宽屏、窄窗口；若目标包含手机，再补真实 iPhone / Safari，桌面视口模拟不能代替实机。

候选桌面目标为 60 Hz 下主要交互 P95 帧间隔接近 16.7 ms，并显著减少超过 33.3 ms 的长帧；最终目标随用户的目标设备确定。画面对照重点是透明内构、侧边高光、阴影接触、文字可读性，以及 LOD 边界没有跳变。没有真机基线前，不承诺“提升几倍”。

本次所有量化结论以当前资产及源码为准。RhineLabUI 旧 `verification/PERFORMANCE-ARCHITECTURE.md` 中的 11 primitive、39,544 个总三角形与旧阵列数据已经不对应当前资源，不能作为这轮优化基线。
